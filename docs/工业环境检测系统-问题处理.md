## 二、已确证的问题

### P-01 · 界面数值无法动态更新

**现象** 概览页六张磁贴卡创建后，数值永远是创建时写死的初始文字。

**定位** 读 `App/ui.c` 的 `data_card()`：它创建了数值 label，但**函数返回的是卡片对象，数值 label 的指针就地丢弃了**。设置页的 `v1/v2/v3` 也是函数内的局部变量，函数一返回就没了。没有句柄，后面没有任何办法改这些文字。

**根因** 原设计只考虑"静态渲染一次"，没有为"动态刷新"预留引用。

**修法** `data_card()` 增加 `lv_obj_t **val_out` 出参，把数值 label 的句柄交出来，存进文件级静态数组；设置页同理。

**教训** LVGL 里每个要改的控件都必须留句柄。**创建时就该想好"以后谁要改它"。**

---

### P-02 · FreeRTOS 堆不够，任务创建静默失败

**现象（潜在）** 新增 3 个任务后系统可能卡死或行为异常。

**定位** 从 `Core/Inc/FreeRTOSConfig.h` 读到 `configTOTAL_HEAP_SIZE = 15360`，从 `main.c` 读到 LVGL 任务栈 `2048*4 = 8192` 字节。手算：

```
总堆                        15,360 B
  − LVGL 任务(8192 栈 + TCB)  8,292
  = 剩                        7,068
  − Sensor(1536 + TCB)        1,636
  − Voc   (1536 + TCB)        1,636
  − Host  (2048 + TCB)        2,148
  = 剩                        ~ 1,648 B
```

（idle 和 timer 任务走 CMSIS-RTOS2 的静态内存，不占这个堆 —— 已从 `cmsis_os2.c` 的 `vApplicationGetIdleTaskMemory` 确认。）

**根因** CMSIS-RTOS2 的 `osThreadAttr_t.stack_size` 单位是**字节**不是字，且任务栈从 FreeRTOS 堆里出。

**修法** 两步：① 收窄三个任务的栈（1.5/1.5/2 KB）；② `TOTAL_HEAP_SIZE` 提到 32,768。

**教训** `osThreadNew` 堆不够时**只返回 NULL，不报错、不提示**，后面用到句柄的地方才会莫名其妙地炸。为此在 `app_tasks.c` 里加了 `configASSERT` 和 `app_tasks_heap_left()` —— 把静默失败变成显式失败。

### P-03 · CubeMX 改的参数没落盘

**现象** 在 CubeMX 里把 `TOTAL_HEAP_SIZE` 改成 32768，但 `FreeRTOSConfig.h` 和 `.ioc` 里都还是 15360。

**根因** 数值框输完没有按回车/没点面板别处就切了标签页，CubeMX 丢弃了未提交的编辑。

**修法** 改完按回车 → `Ctrl+S` 存 `.ioc` → Generate Code。

**验证方法** `grep TOTAL_HEAP F407_ILI9341_LVGL_FreeRTOS.ioc` 应显示 `32768`。

**教训** CubeMX 里改完**一定要回读文件确认**，别信界面。"我在 GUI 里改过了"和"文件里真的是这个值"是两件事。

---

### P-05 · `DMA Continuous Requests` 灰掉不可选

**现象** ADC1 参数页里 `DMA Continuous Requests` 只能停在 Disabled，Enabled 不可选。

**根因** CubeMX 的依赖关系：要先满足 ① 在 DMA Settings 里加好 DMA 请求，② `Continuous Conversion Mode = Enabled`。

**修法** 补齐这两项后解锁，改为 Enabled。

**备注** 该项对应 F4 的 `ADC_CR2.DDS` 位。设为 Disabled 的话，DMA 搬完设定个数后不再产生新请求，循环缓冲区会**冻在第一次的值上**，界面上表现为"数字纹丝不动"。这一条是 ADC 三路能出数的前提。

### P-07 · DMA 中断的 NVIC 勾选被 CubeMX 锁死

**现象** 在 ADC1 的 NVIC Settings 页和全局 NVIC 表里，`DMA2 stream0 global interrupt` 的使能勾都是灰的，取消不掉。

**分析** 循环模式下"传输完成"每约 14 µs 一次 → **约 7 万次/秒**中断。而 `Task_Sensor` 是 100 ms 主动取一次值，完全不需要中断通知。留着大约白烧 9% CPU。

**修法** 在 `main.c` 的 `USER CODE BEGIN 2` 里反向关掉：

```c
HAL_NVIC_DisableIRQ(DMA2_Stream0_IRQn);
```

放在 USER CODE 区，CubeMX 重新生成不会丢。`HAL_ADC_Start_DMA` 只在 DMA 控制器内部开 TC 中断位，不碰 NVIC，所以 NVIC 关掉不影响 DMA 硬件搬运。

**教训** CubeMX 不给你关的东西，很多时候可以"生成之后再关"，且仍然保持"重新生成不丢"。优先用 USER CODE 区解决，而不是去改生成的文件。

### P-08 · 校准函数不存在

**现象** 准备调用 `HAL_ADCEx_Calibration_Start()` 做 ADC 自校准，查证时发现链接不过。

**定位** 全项目搜索 `Calibration`：`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_adc_ex.c` 里只有注入通道和多模式相关函数，**没有校准**；`stm32f4xx_hal_adc.c` 里也没有，`HAL_ADC_Init` 内部同样不做。

**修法** 不做软件校准。理由：不校准的误差只有几个 LSB，折算到 0~100 相对指数上不到 0.1 个点；而两点标定本来就会把这类系统误差吸收掉。

**教训** 用 HAL API 之前先 `grep` 确认它在这个版本里真的存在。不同 HAL 版本的 API 集合不一样，照着手册/网上例程写会直接链接失败。（这次是"写之前先查"，属于运气好。）

### P-09 · 数值只显示一个字母 `f`

**现象** 概览页"烟雾 / 有毒气体 / 光照"三张卡不显示数字，只有一个字母 `f`。设置页的六个阈值滑块却一切正常。

**定位** 观察到只有用 `%.0f` 格式串的三张卡出问题，用 `%ld` 的滑块正常 → 指向 `%f`。

查证链：

1. `LVGL/lv_conf.h` → `LV_SPRINTF_USE_FLOAT 0`
2. `LVGL/lvgl/src/misc/lv_printf.c` → `PRINTF_DISABLE_SUPPORT_FLOAT` 为真时，`case 'f'` 整块被 `#if` 编译掉
3. 于是 `%f` 掉进 default 分支，而 default 分支把格式符**原样输出** → 屏幕上只有一个 `f`

**根因** LVGL 用的是自己实现的 printf（`lv_printf.c`），不是 libc 的 sprintf，默认不编浮点格式化。

**修法** `lv_conf.h` 里 `LV_SPRINTF_USE_FLOAT` 改为 `1`（约多占 4.5 KB Flash，当前 Flash 仅用 41%，无所谓）。

**教训** LVGL 的格式化是独立实现，**用任何格式符之前要确认 LVGL 支持它**，不能想当然按 C 标准库的行为推断。另外这个 bug 有很强的**误导性**：它让"ADC 到底通没通"变得不可判断 —— 不管读到多少都显示 `f`。所以它排在最前面修。

### P-10 · 开关回调文案串了

**现象（自查发现）** 拨动"报警提示音"开关，弹出的 toast 写的是"自动通风已开启"。

**根因** 两个开关共用 `on_switch()` 回调，但 toast 文案写死了"自动通风"，没有按控件区分。

**修法** 在回调里用句柄判断是哪一路，分别给对应文案。

**教训** 共用回调（表驱动）能省掉大量重复代码，但**凡是"因控件而异"的部分都必须参数化**，否则就会像这样串味。这类 bug 不会让功能失效，只会让界面说假话。

### P-12 · 宏重定义导致改了不生效

**现象** 把 `voc.h` 里的 `VOC_TIMEOUT_MS` 从 3000 改成 10000，实际行为没变化。

**定位** 编译器警告：

```
app_tasks.c:51:9: warning: "VOC_TIMEOUT_MS" redefined
   51 | #define VOC_TIMEOUT_MS  3000
voc.h:43:9: note: this is the location of the previous definition
```

`app_tasks.c` 里还留着最初写空壳时的那份定义，它在 `#include "voc.h"` **之后**。

**根因** C 语言的宏重定义规则是"**后定义的赢 + 一句警告**"，不报错。所以在 `app_tasks.c` 这个编译单元里，超时一直是 3000，`voc.h` 的值被静默覆盖。

**修法** 删掉重复定义，协议相关常量统一归 `voc.h` 管，原位置留注释说明原因。

**教训** **这是本次最难发现的一类 bug**：改一处完全不生效，而去读被改的那个文件看不出任何异常。只有编译器警告能发现。所以：
- **不要过滤掉编译警告**（哪怕只是为了看"有没有 error"）
- 同一个宏只在**一个**地方定义，其它文件通过 `#include` 获取

### P-13 · 反相传感器标定后会退化成常量

**现象（预防性修复）** 光敏模块是**反相**的（越暗 AO 越高）。如果按标定说明填端点，`raw100 - raw0` 会算出负数。

**根因** 原标定代码写的是 `if (span > 0)`，负数会掉进兜底分支返回 0，再经过输出端的 `100 - x` 反相就**恒定显示 100**。不报错、不警告。

**修法** 两处改动：① `span > 0` 改成 `span != 0`，让除法自然处理符号；② 去掉输出端的 `100 - x`。

**设计取舍** 原本有**两套**反相机制（标定端点顺序 + 输出端 `100 - x`），二者会互相干扰。现在只保留一套（标定 + 允许负 span），于是三个通道的填表规则统一成"**0 点工况量到多少填 raw0，100 点工况量到多少填 raw100**"，不需要记谁是反相的。

**教训** 同一个效应只用一个机制表达。**两个机制叠在一起，改一处忘一处，而且往往不报错。**

### P-14 · 下行命令每条的最后 1 个字段永远不生效

**现象（PC 单测发现，未上硬件）** 上位机发 `$SET,1,T=32,H=55,CO2=1500,SMK=20,GAS=25,LUX=40*XX`，前 5 个字段都改了，**只有最后一个 `LUX` 改不动**。

**定位** 看失败模式："只有命令的最后一个字段失败"，说明问题出在字段边界的处理上，而不是某个字段的解析逻辑。

回看 `host_parse_cmd()`：它用 `strrchr(line, '*')` 找到校验段来验校验和，**但没有把 `*XX` 从正文里切掉**，随后直接拿 `line + 1` 去按逗号切字段。于是最后一个字段变成了 `LUX=40*7A`，`parse_x10()` 看到尾部的 `*` 就判定格式非法，整个字段被忽略。

校验和本身是对的，所以帧能通过校验、前面的字段也正常生效 —— **只有最后一个永远是哑的**。

**修法** 先把 `'$'` 之后、`'*'` 之前的正文拷进一个局部缓冲，再对这份干净的正文切字段。

**教训**

1. 这类 bug **在板子上极难查**：表现是"有些字段能改、有些不能改"，而"能改的"还会随命令内容变化（谁排最后谁失效）。看起来完全像随机故障。
2. 它是靠**主机侧单元测试**抓到的 —— 协议层是纯整数运算、不依赖硬件，可以直接在 PC 上编译运行。**能脱离硬件验证的逻辑，就不要等到上板再试**（见 M-07）。

### P-15 · 下位机收到的命令"完全没反应"

**现象** 上位机发 `$SET,1,T=30*19`，屏幕上的温度阈值滑块纹丝不动。但**同一条串口上，下位机的遥测帧每 500ms 正常收到**。

也就是：**发送链路（下位机 → 上位机）完全正常，接收链路"看起来"不通。**

**定位** 这次没有靠猜 —— 之前为了排查接受的链路诊断计数器直接给出了答案：

| | 发送前 | 三次发送后 | 差值 |
|---|---|---|---|
| `RXB`（收到的字节总数） | 210 | 252 | **+42** |
| `RXL`（收满的行数） | 0 | 0 | 0 |
| `RXO`（生效的命令数） | 0 | 0 | 0 |

按了 3 次发送，`42 ÷ 3 = 14` 字节，**正好是 `$SET,1,T=30*19` 的长度**。

**结论：命令正文一个字节不差地收到了，但后面什么终止符都没有。** 于是行永远收不满（`RXL` 恒为 0），解析器根本没被调用。

**根因** 上位机那边用的是串口助手 UartAssist V5.0.10，界面上勾了 `自动发送附加位`，但**它在这个例子里并没有产生任何附加字节** —— 工具自己的发送日志写着 `SEND ASCII/14`，和 `RXB` 的增量互相印证。

**修法** 不依赖工具那个勾的语义，**在发送框里把终止符显式写出来**：

```
$SET,1,T=30*19\r\n
```

因为 `转义符自动解析` 这个选项是可靠的（它把字面的 `\r\n` 变成真正的回车+换行）。改完立刻生效，日志变成 `SEND ASCII/16`。

**教训**

1. **这类 bug 从固件角度几乎不可见。** 固件没收到终止符，所以它"什么都没做" —— 而"什么都没做"和"收到了但校验不过""收到了但解析崩了"从外部看**完全一样**。必须靠中间量区分（见 M-01）。
2. **ASCII 协议里行终止符是非常脆弱的一环。** 不同串口助手的默认行为不一样（`\r\n` / `\n` / `\r` / 完全不补）。所以固件后来改成**三种都接受**，把这一环的脆弱性从设备侧去掉。
3. **不要相信工具界面上一个勾的名字。** `自动发送附加位` 听起来像"自动补 CRLF"，但它在这个工具的这个版本、这个发送模式下没有附加任何字节。**以实际发出的字节数为准** —— 工具的发送日志 + 设备的接收计数，两边一对照就清楚了。

**附带发现：溢出保护救了这一局**

用户前面十几次尝试，往行缓冲里倒进了 128 字节，全都在等一个永远不会来的终止符。第一个真正的 `\r\n` 到达时，缓冲区里已经有 128 字节 > 96 字节的行缓冲上限 → 触发溢出保护，**整行丢弃**，所以那一次仍然没生效；第二次才通。

如果当初没有"溢出就整行丢掉、等下一个终止符重新对齐"这个设计，那 128 字节垃圾会**永远留在缓冲区里**，之后每一条命令都被拼在垃圾后面，校验永远不过 —— 变成不可恢复的死锁，只能重启。

## 三、未确证的问题

### P-11 · 21VOC 三张卡一直显示占位符

**现象** `Task_Voc` 写完后，温度/湿度/CO2 三张卡一直显示 `---.-°C` / `--%` / `---- ppm`，从不出现真实数值。屏幕操作正常（排除 `configASSERT` 卡死）。

**已知事实**

- 加了诊断计数器后，两个数都在涨：字节数在涨、通过校验的帧数也在涨
- 帧数涨 ⟹ `voc_parse()` 通过 ⟹ `env_set_voc()` 被调用 ⟹ `voc_online = true`
- 实测上报间隔 **1 秒一帧**（60 秒收到 60 帧）

**推理**

界面上只有 `voc_online` 长期为 false 才会一直显示占位符。而 `voc_online` 变 false 只有两条路：

1. `env_set_voc_lost()` 被调到（超时判定）—— **排除**：超时当时是 3 秒，而帧 1 秒一帧，超时计时每 1 秒就被重置，永远触发不到
2. 从来没收到过合法帧 —— 但计数器证明收到了

**所以：代码侧的两条路都被排除，而收帧这条链在两个版本之间代码完全一致**（期间只加了计数器、改了显示）。

**结论：根因未锁定**，最可能是物理层问题（接线/供电/接触）在排查过程中被顺带解决。**不能排除"调代码时顺手把线接对了"这种巧合。**

**保留的诊断手段** 两个计数器保留在 `env_t` 和 `voc.c` 里，界面显示由 `ui.c` 顶部的 `VOC_DEBUG_UI` 开关控制（当前为 0）。下次同类问题第一步就打开它。

## 四、认知纠正（不是 bug，但曾经理解错）

### C-01 · 模拟模块上的电位器不校准 AO

常见四针模块（VCC/GND/DO/AO）的板载电路是**两条互不相干的支路**：

```
              VCC (5V)
                │
        ┌───────┴────────┐
        │                │
     [气敏 Rs]        [电位器] ← 只在这条支路上
        │                │
        ├──→ AO          ├──→ LM393 参考输入
        │                │
     [负载 RL]        [另一端 GND]
        │
       GND

   AO = VCC × RL / (Rs + RL)     ← 电位器完全不参与这个计算
```

- **AO 是敏感元件与负载电阻的分压直出**，随气体/光照变化，**不随电位器变化**
- **电位器接在 LM393 比较器的一个输入上**，只决定 DO（数字输出）在什么电平翻转，并控制板载 LED
- 所以"出厂校准过"只是指厂家把电位器拧到一个大概能用的位置，**没有计量意义**

**30 秒验证法** 一边盯着 ADC 读数一边拧电位器 —— AO 读数纹丝不动，板载 LED 会在某处翻转。

**为什么不走 DO** DO 的阈值只能用手拧螺丝刀，而本项目需求是**上位机远程设置阈值**，所以必须走 AO + 软件阈值。

### C-02 · 纯模拟量没有绝对单位，必须两点标定

除 21VOC（数字输出、出厂标定）外，光敏 / MQ-2 / MQ-7 都是纯模拟量，**不存在"正确值"**，想要 lx / ppm 需要专业标定设备。因此统一归一化成 **0~100 相对指数**。

两端点由自己造，不需要买仪器：

| 通道 | 0 点 | 100 点 |
|---|---|---|
| 光敏 | 手指完全盖住 / 塞进抽屉 | 手机手电筒贴近照 |
| MQ-2 | 开窗通风静置 5~10 分钟 | 酒精棉片放在旁边（别贴上去） |
| MQ-7 | 同上，干净空气就是 0 | 打火机气在旁边释放 |

**三个注意点**

1. MQ 系列**必须先预热**（约 5 分钟）再测 0 点，刚上电漂移很大
2. **打火机气千万别对着 21VOC 模块喷** —— 该模块说明书明确写了会对这个 MEMS 传感器造成极大损害。MQ 是半导体式，用打火机气没问题，但要离远点
3. 标完气体后 MQ 基线要几小时才恢复，所以顺序是**先标光敏（无污染）、再标气体**

### C-03 · `lv_timer_handler()` 不是"刷新一帧"

它是 LVGL 的引擎心跳：跑内部定时器、读输入设备、判断哪些区域脏需要重绘。重绘时才回调 `lv_port_disp.c` 的 `disp_flush()`。所以**一帧要不要重绘由 LVGL 自己决定**，不是每调一次就推一屏。真正的像素搬运由 SPI1 的 DMA 完成。

### C-04 · 工程里有**两套** printf，浮点支持是分开配的

这个工程里同时存在两个 printf 实现，**各自独立配置**，很容易只配了一个就以为都好了：

| | 实现 | 浮点开关 | 本工程状态 |
|---|---|---|---|
| 界面文字 | LVGL 自己的 `lv_printf.c` | `LV_SPRINTF_USE_FLOAT`（在 `LVGL/lv_conf.h`） | **已设为 1** |
| 组帧 / 日志 | libc（newlib-nano） | 链接参数 `-u _printf_float` | **没有加** |

本工程的链接参数是 `--specs=nano.specs` 且**没有** `-u _printf_float`，所以 newlib-nano **不支持浮点格式化**。在这个前提下写 `snprintf(buf, n, "%.1f", t)` 会**静默输出空字符串**，不报错、不警告 —— 和 P-09 是同一类失败。

**当前对策** `host_proto.c` 全程整数运算，温度湿度按"放大 10 倍的整数"自己拼字符串，完全不依赖任何库的浮点支持。（如果哪天确实需要 libc 的 `%f`，在根 `CMakeLists.txt` 里加 `target_link_options(... PRIVATE -u _printf_float)` 即可 —— 那个文件是"只生成一次"的，不会被 CubeMX 覆盖。）

## 五、可复用的排查方法

### M-01 · 把中间量显示出来，别靠猜

排查"传感器没数据"这类问题时，最大的浪费是在两个方向上盲猜。**先把链路切成几段，把每段的中间量变成看得见的东西**，一次就能砍掉一半可能性。

P-11 的排查就是靠这个：加两个计数器（收到的字节数 / 通过校验的帧数）显示到屏幕上。

```
两个数都不动          → 字节根本没到 MCU（接线/供电/波特率）
字节涨、帧数不涨      → 字节到了但凑不成合法帧（波特率/帧头/校验）
两个都在涨            → 链路是通的，问题在别处
```

代价只是几行代码，收益是"不用猜"。

### M-02 · 先查"依赖链"再怀疑硬件

P-09（`f`）和 P-11 都是**看起来像硬件故障、实际是软件问题**的典型。判断方法：看症状**有没有选择性**。

- `f` 只出现在用 `%f` 的三张卡上，用 `%ld` 的滑块正常 → **有选择性 → 软件问题**
- 三张卡全是占位符、但屏幕操作正常 → 需要进一步分段

### M-03 · 编译警告必须看

P-12 的宏重定义**只有编译器警告能发现**，读代码永远看不出。所以构建流程里**不要用 `grep -i error` 过滤掉警告**，要么全看，要么单独统计警告条数。

### M-04 · 改动一次只改一处，改完立刻验证

P-11 的根因没能锁定，很大程度上是因为当时**同时**改了多处（计数器 + 显示 + 超时值），而期间接线状态也可能变了。多个变量同时变化时，事后无法归因。

### M-05 · CubeMX 里改的东西一定要回读文件确认

界面上"改过了"和文件里真的是那个值，是两件事（见 P-03、P-12）。

### M-06 · CubeMX 不让你改的，往往可以在 USER CODE 区"生成后再改"

见 P-07。优先用 USER CODE 区，而不是去改生成的文件 —— 既解决问题，又不会被下次重新生成覆盖。

### M-07 · 能脱离硬件验证的逻辑，就在 PC 上单测

**协议解析、数据结构、算法这类"纯逻辑"和硬件无关**，用该平台的主机编译器直接编出来跑就行，不用等烧录、不用接线、还能构造硬件上很难造的输入。

P-14 就是这样抓到的（63 项断言，跑一次一秒）。而同一个 bug 如果留到板子上，表现是"有些字段偶尔改不动"，可能要查一整天。

做法：

```bash
gcc -std=c11 -Wall -Wextra -I App tests/test_host_proto.c App/host_proto.c -o test && ./test
```

注意：测试文件**不要放进 `App/`**，因为工程用 `file(GLOB App/*.c)` 收集源文件，放进去会把带 `main()` 的测试链进固件。放 `tests/` 单独编。

**判断标准**：这段代码如果只是"输入→输出"，没有寄存器、没有外设、没有 RTOS 调用，那就该测。
