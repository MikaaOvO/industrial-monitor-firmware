## 一、这个上位机要干什么

来自硬件台账的"需求覆盖"表：

| 需求 | 上位机侧要做的事 |
|---|---|
| 上位机通信 | 通过串口接收下位机主动上报的环境数据 |
| **数据记录** | 把收到的数据存下来（CSV / 数据库），能看历史 |
| **阈值设置** | 把 6 个报警阈值下发给下位机，并能**回读确认是否生效** |
| 风扇控制 | 下发"自动通风 / 手动通风"开关 |
| 状态监视 | 显示报警等级、21VOC 在线状态、以及**链路自身的通断情况** |

## 二、连什么

下位机有**两条功能相同、可以同时使用的串口链路**：

| 链路 | 下位机侧 | 你这边需要 | 用途 |
|---|---|---|---|
| **调试链路** | USART2（PA2/PA3） | **CH340 USB 转 TTL** | 开发调试。用串口助手就能直接看，最省事 |
| **工业链路** | USART6（PC6/PC7）+ MAX3485 | **USB 转 485 适配器**（光耦隔离） | 正式演示。模拟工业现场的总线组网 |

两条链路跑的是**完全相同的协议**，参数都是 **115200 8N1**。

> 下位机侧两条链路**同时可用**，遥测会同时往两条发；命令从任一条下发都生效。
> 所以你开发阶段用 CH340 就行，最后演示换 485。

**实现现状（2026-10-13）**：CH340 那条**已实测通**（遥测 + 命令 + 阈值回读都验证过）；
RS485 那条**硬件在接、固件在改**，协议层会按链路分开维护接收缓冲。

## 三、开始之前必须知道的四件事

这几条都是这个项目真实踩过的坑，写在这里省你走弯路。

### ① 发送命令**必须带行终止符**

下位机的行解析以 `\r` 或 `\n` 收尾。少了它，**命令会完全没反应**，而且从下位机角度看"什么都没发生"—— 排查时会以为是接线或者固件问题。

实际踩过的场景：串口助手上勾了"自动发送附加位"，但它并没有真的补换行，导致连续十几次发送一个字节都没生效。

**Qt 侧的正确做法**：拼帧时直接带上 `"\r\n"`，不要依赖别的层替你补。

### ② `SMK` / `GAS` / `LUX` 是 **0~100 相对指数**，不是物理单位

这三个是模拟量（烟雾 / 有毒气体 / 光照），没有绝对单位，是用两点标定归一化出来的相对指数。

**报告和界面里都不要写成 ppm / lx。** 而且换房间、换传感器就得重新标定 —— 所以**同一个指数值在不同环境下含义不同**，不要拿来跨设备比较。

另外三个（温度 / 湿度 / CO₂）来自 21VOC 模块，是出厂标定的数字量，有真实单位。但注意 **`CO2` 是 eCO₂ 等效估算值，精度 ±25%**，不是真 CO₂ 测量。

### ③ `LINK=0` 时，温湿 / CO₂ 是**过期值**

21VOC 模块掉线后，那几路数据保持最后一次的值不变。**存档前必须看 `LINK`**，否则数据库里会混进一批看不出问题的假数据。

### ④ 命令发出去 ≠ 生效

下位机**会钳制超范围的值**（比如把温度阈值设成 999 会变成 40），也会忽略校验不过的帧。

**确认生效的正确方式**：发完命令后看后续帧里的 `SPT`~`SPL` 是不是变成了你发的值 —— 那六个字段是**下位机当前实际在用**的阈值。

## 四、协议速查

完整规格见 [工业环境检测系统-通信协议.md](工业环境检测系统-通信协议.md)。这里只放最常用的：

```
上行（下位机 → 上位机，每 500ms 自动来一帧）
  $ENV,1,T=22.3,H=56.6,CO2=362,...,ALM=0,LINK=1,...,SPT=30.0,...*24\r\n

下行（上位机 → 下位机）
  $SET,1,T=30*19                                  改温度阈值
  $SET,1,T=28,H=70,CO2=1000,SMK=15,GAS=15,LUX=30*33   六个阈值全量下发
  $FAN,1,AUTO=1,MAN=0*18                          开自动通风
  $FAN,1,MAN=1*36                                 开手动通风
```

**校验和** = `$` 和 `*` 之间的字符逐字节异或，两位**大写十六进制**。Qt 侧的现成代码在协议文档第六节。

**别手写校验和** —— 用 `makeFrame()` 那种拼接函数。手算很容易错，而错了之后的现象是"下位机不响应"，和"终止符没发"一模一样，很难区分。

## 五、建议的推进顺序

1. **先用串口助手（不用写代码）** 连 CH340，确认能收到 `$ENV` 帧、能发通一条 `$SET`。
   这一步不通过，写 Qt 只会把问题叠加起来。
2. **Qt 里先只做"收"** —— 打开串口、按 `\n` 切行、验校验和、把字段解析成结构体、打印出来。
3. **再做"发"** —— 先发一条写死的 `$SET`，然后用 `SPT` 回读确认生效。
4. **然后才是界面**：数值显示 → 阈值设置控件 → 数据记录（CSV）→ 曲线。
5. **最后接 RS485** —— 协议层完全不用改，只换串口号和适配器。

## 六、可用的调试信号

下位机的遥测帧里有三个**链路诊断计数器**，专门用来判断"命令为什么没生效"：

| 字段 | 含义 |
|---|---|
| `RXB` | 下位机在这条链路上收到的字节总数 |
| `RXL` | 收满的行数 |
| `RXO` | 校验通过并生效的命令数 |

| 现象 | 结论 | 该查什么 |
|---|---|---|
| `RXB` 不涨 | 字节没到下位机 | 接线（TX/RX 是否接反）、共地、波特率 |
| `RXB` 涨、`RXL` 不涨 | 字节到了但凑不出整行 | **行终止符**（见第三节 ①） |
| `RXL` 涨、`RXO` 不涨 | 行收满了但校验不过 | 校验和算错了 |
| `RXO` 在涨 | 命令生效了 | 没问题 |

**建议把这些提示直接做进 Qt 界面**（比如状态栏显示"下行链路正常 / 命令未被接受"），
比让用户去猜专业得多。
